# 03 · 安全、加密与密钥设计

## 1. 威胁模型和边界

目标是降低服务器磁盘泄露、备份泄露、代理日志泄露和传输窃听导致的正文暴露。正文在上传前由客户端加密，服务端不持有内容主密钥。TLS 同时保护登录凭据、访问令牌及元数据。

服务端仍能观察账号、设备名/平台、条目数量、密文长度、访问 IP、服务器时间及删除状态；这不等于完全匿名。密钥已解锁的客户端、操作系统剪贴板、屏幕、恶意输入法、管理员控制的终端和客户端供应链不在“服务器无法读正文”的保障内。

AEAD 可检测密文篡改及上下文替换，但不阻止恶意服务器拒绝服务、删记录或对全新设备隐藏历史。序号和本地最高版本防止普通重复/倒退；首版不声称具备恶意服务器可验证日志或前向保密。

## 2. 账号认证与内容加密分离

| 材料 | 生成/保存 | 用途 |
| --- | --- | --- |
| 登录密码 | 用户输入；服务器只保存独立盐的 Argon2id PHC 字符串（本地账号）或由外部站点验证 | 验证账号身份；客户端另用 Argon2id 派生密码包装密钥，服务端只存密文信封 |
| 内容主密钥 CMK | 首台客户端 CSPRNG 生成 32 字节；客户端安全保存 | 按条目派生加密密钥 |
| 恢复密钥 RK | 首台客户端 CSPRNG 生成独立 32 字节，用户离线保存 | 备用包装密钥；密码丢失或换设备且本地无 CMK 时使用 |
| 本地保护密钥 | Windows 用户密钥保护 / Android Keystore | 包装本地 CMK、令牌、离线队列密钥 |
| 会话令牌 | 服务端 CSPRNG，访问和刷新各 32 随机字节 | API 认证；数据库只存 SHA-256 摘要 |

Argon2id 初始基准建议内存 64 MiB、迭代 3、并行度 1，经目标服务器压测后确定；这是项目参数草案，不替代安全评审。限制登录并发和请求速率以防内存耗尽。密码不截断、不 trim、不记录；客户端和服务端限制 UTF-8 输入字节数，例如 12–128 字符且 ≤512 字节。

访问令牌有效期 15 分钟，刷新令牌绝对寿命 30 天；每次刷新轮换并保存已使用摘要用于重用检测。重用撤销该刷新族。客户端同设备只运行一个刷新任务，并发刷新不得制造误报。网络丢失刷新响应时，首版可要求重新登录，不能静默接受旧刷新令牌无限重放。

每个请求检查会话到期、设备撤销、账号状态。已有 WebSocket 每 60 秒复查并在撤销提交后主动关闭；访问令牌到期关闭并刷新重连。登录和刷新响应 `Cache-Control: no-store`。WebSocket 原生客户端通过 Authorization 请求头认证，不把长期令牌放 URL。

## 3. 首次初始化与新设备

1. 注册创建 `user_id`，服务端返回 `vault_initialized=false`。同一个账号允许登录查看设备，但保险库未初始化时不能写条目。
2. 客户端生成 `vault_id`、CMK、RK、32 字节 `wrap_salt` 与 12 字节 `wrap_nonce`，以及独立的密码包装信封；密钥版本 `key_epoch=1`。
3. 显示恢复码 `oc1_` + RK 的无填充 base64url（43 字符）；可视觉分组，导入时只去除界面允许的分组空格；前缀、长度、字节范围严格校验。它是高熵随机密钥，日常解锁改用登录密码包装，RK 只作备用。
4. 用户离线保存并确认后，上传 CMK 信封（可同时带 `password_wrap`），使用 `PUT /vault` + `If-None-Match: *`。数据库对 `user_id` 唯一，两个初始化请求只有一个成功；失败端销毁候选 CMK，重新获取已存在保险库并要求其恢复码，禁止覆盖。
5. 登录成功后客户端按顺序尝试：本机已保护的 CMK、服务器上的密码包装信封、用户输入的恢复密钥。成功后以系统密钥机制保护 CMK，并在信封缺失或与当前密码不匹配时 `PUT /vault/password-wrap` 补写。
6. RK 不提交服务器，也不默认写入应用日志、崩溃报告或系统剪贴板。服务端“忘记密码”只能重置认证并撤销会话；密码变更后旧密码信封失效，需本机 CMK 或 RK 再包装。所有设备失去 CMK 且 RK 丢失，则历史不可恢复。

恢复码丢失但旧设备还可解锁时，首版允许从旧设备安全显示之前保存的恢复材料，或重新登录继续使用旧设备；是否持久保存 RK 应明确为用户选择，默认只持久保存 CMK。**若未保存 RK，仅有 CMK 的设备不能凭空重建原 RK。** 重新包装/轮换恢复码属于 P1，需要单独 CAS API 和安全确认；首版不要给出不存在的“重置恢复码”按钮。所有设备失去 CMK 且 RK 丢失，则历史不可恢复，管理员不能解密。

## 4. 密码学格式 v1（待双端互通验证）

所有 UUID 是小写、带连字符的标准 36 字符形式；整数的文本表达不带前导零；协议二进制字段使用 RFC 4648 base64url 无 `=`；禁止接受多种非规范编码后默默重写。GCM 标签固定 16 字节，nonce 固定 12 字节。

### 4.1 CMK 包装

```text
wrap_info = UTF8("onlineclipboard/v1/wrap")
KEK = HKDF-SHA256(IKM=RK, salt=wrap_salt, info=wrap_info, L=32)
wrap_aad = UTF8("oc-v1|vault|" + user_id + "|" + vault_id + "|1")
wrapped_key = AES-256-GCM(KEK, wrap_nonce, plaintext=CMK, AAD=wrap_aad)
```

`wrapped_key` 按 `ciphertext || tag` 组合，共 48 字节；字段另外保存 `wrap_salt`、`wrap_nonce`、`vault_id`、`key_epoch`、`format_version=1`。`user_id` 使用登录得到的账号 ID，客户端不可用信封里任意另一个账号替代预期值。

### 4.1.1 登录密码包装

服务端只保存不透明信封，从不接收明文密码用于解密，也不持有 CMK。

```text
password_ikm = Argon2id(password, kdf_salt, t=3, m=65536 KiB, p=1, L=32)
wrap_info = UTF8("onlineclipboard/v1/wrap-password")
KEK = HKDF-SHA256(IKM=password_ikm, salt=wrap_salt, info=wrap_info, L=32)
wrap_aad = UTF8("oc-v1|vault-password|" + user_id + "|" + vault_id + "|1")
password_wrapped_key = AES-256-GCM(KEK, wrap_nonce, plaintext=CMK, AAD=wrap_aad)
```

`kdf_salt` 16 字节，`wrap_salt` 32 字节，`wrap_nonce` 12 字节，`password_wrapped_key` 48 字节。KDF 标识固定 `argon2id`。参数可在信封中携带以便日后提高成本，但服务端校验范围：time 1–10、memory 8192–262144 KiB、parallelism 1–4。密码包装与 RK 包装互不影响；改密后旧信封无法打开，客户端用本机 CMK 或 RK 重新上传。

### 4.2 条目加密

```text
item_info = UTF8("onlineclipboard/v1/item|" + clip_id + "|" + key_epoch)
item_salt = UTF8(vault_id)
K_item = HKDF-SHA256(IKM=CMK, salt=item_salt, info=item_info, L=32)
aad = UTF8("oc-v1|clip|" + user_id + "|" + vault_id + "|" +
           clip_id + "|" + source_device_id + "|" + key_epoch + "|text/plain")
nonce = CSPRNG(12)
ciphertext = AES-256-GCM(K_item, nonce, plaintext=UTF8(text), AAD=aad)
```

同样把 tag 接在 ciphertext 末尾；不发送可由客户端自行替换的 `aad` 字段，解密端按协议从已验证的上下文重建。正文允许 1–65,536 字节，密文含标签允许 17–65,552 字节。初版不压缩、不进行正文规范化。标题/预览从本地解密正文生成；以后增加内容注释时放入新版加密载荷。

条目 ID 为客户端生成的 UUIDv4，正文一经创建不可改。一次加密后将**相同的整个信封**存进 outbox，网络重试原样发送。不能用相同 key/nonce 加密另一份内容；需要编辑时生成新 ID、新 nonce。服务端对同 ID 不同信封返回 409。

密钥派生采用成熟实现，Windows 可用系统 HKDF/AesGcm；Android 使用已评审 HKDF 实现和 `AES/GCM/NoPadding`。两端标签拼接方式一致。开发前以 [互通向量](../contracts/README.md) 验证；禁止自行设计密码算法或把 CBC/ECB 替换为“兼容方案”。

## 5. 本地保护、搜索与敏感内容

- Windows 以当前用户作用域 DPAPI/等价平台保护包装随机本地存储密钥；Android Keystore 中生成不可导出包装密钥，硬件保护有则使用，不假设所有机型都有。
- 使用不同派生上下文保护本地令牌和 outbox；网络 CMK 与本地密钥用途分离。SQLite 普通行只存密文、非敏感元数据；含文本的待上传命令也必须加密。
- 搜索索引只在内存存活，锁定/退出时丢弃。若未来采用磁盘 FTS，必须采用包含 journal/WAL 的数据库加密方案，不能只加密正文列然后另建明文索引。
- Android 禁止将密钥/令牌/账号缓存自动备份到云；重装后按新设备解锁。锁屏后暂停明文处理及自动写入，恢复后历史补偿不自动覆盖剪贴板。
- 被系统标为敏感的内容默认跳过自动上传；Windows 应用排除名单和短期暂停供用户选择。正则识别密码/验证码仅是辅助，不能保证识别所有秘密。
- 远端文字写入 Android 剪贴板时可默认打敏感预览标记；它控制预览，不代表系统剪贴板已经加密，也不会保护其他可读取应用。
- 不上传源应用名称、窗口标题或正文哈希；本地防重复指纹用独立随机本地密钥做 HMAC，短时持有，不作为服务端索引。

## 6. 撤销与密钥轮换

撤销设备立即阻止后续服务访问，但不能收回它已下载的明文、密文和 CMK。首版同账号共享 CMK，撤销不自动带来密码学隔离。若设备疑似泄露，用户需停止同步，迁移到新保险库/账号并重新加密仍需保留的历史；迁移不能删除攻击者副本。

`key_epoch` 为未来轮换预留；v1 服务只接受 epoch 1。P1 实现轮换时，必须包括新 CMK、仍受信设备授权、旧历史重加密、旧恢复码失效、离线设备再授权及事务切换，不能仅加一个 epoch 数字即宣称完成安全撤销。

## 7. 服务端防护要求

- 所有资源查询显式绑定认证 `user_id`；不接受请求体中的用户 ID 决定所有者；错误资源统一 404 避免跨账号枚举。
- 限制 JSON 请求体、base64 解码长度、分页上限和连接数；验证全部信封字段/版本，服务器无法验证内容真实性但能校验形状。
- 默认邀请注册；邀请码高熵、一次性、过期、只保存摘要。管理员重置密码命令通过终端隐式输入，不在进程参数写密码。
- 日志只含请求 ID、路由模板、状态码、耗时和脱敏用户标识；不含 URL 查询中的凭据、请求正文、密码、令牌、恢复码、密钥或正文预览。
- 配置证书验证失败必须停止，不提供“信任所有证书”开关。导入私有 CA 的流程明确展示信任范围。
- 正式版审查依赖、SBOM、更新包签名、Windows 代码签名和 Android APK 签名；用户可停用更新检查，不强制中心化服务。

## 8. 删除与备份语义

7 天清理针对在线业务库的内容密文；删除事件、条目 ID 登记和必要元数据可更久保存以防复活，不包含正文。SQL DELETE 不等于底层介质立即覆写；WAL、旧备份及已有客户端副本按各自保留周期处理。运维应定义备份保留期并告知用户，不能宣称“7 天后全世界所有副本不可恢复”。
